# 熱中症対策・体調管理 Webアプリ 基本設計書（ドラフト）

領域の定義は `docs/spec/` の D01〜D18。本書の章立ては領域の境界と一致しない。要求を直すときは領域のファイルを更新する。

| 項目 | 内容 |
| --- | --- |
| 文書種別 | 詳細仕様書ドラフト（基本設計） |
| 対応する要件 | `docs/01-requirements.md` |
| 状態 | 画面・データ・判定・認証の実装方針。閾値、設問原文、顔認証製品、通知チャネルは仮または未接続 |

本書は実装の骨格である。医療判断の数値と、既存顔認証システムの接続仕様は発注者確認後に確定欄へ移す。

## 1. 構成

### 1.1 論理構成

| 層 | 責務 |
| --- | --- |
| 作業者Web | QRランディング、言語、本人確定、2種のフォーム、周知コンテンツ、送信 |
| 管理Web | ログイン、一覧、詳細、アラート、マスタ、抽出 |
| API | トークン検証、回答保存、判定、権限、通知、監査 |
| DB | 現場、アカウント、作業者、回答、判定、対応、お知らせ、辞書の元データ |
| 通知ワーカー | 赤判定のメール（および将来のチャット） |
| 顔認証（外部） | 低コスト時は本システム外。トークン付きURLを発行する側。本システムは検証だけ持つ |

顔画像と生体特徴量のテーブルは作らない。

### 1.2 URL（案）

| パス | 画面 | 認証 |
| --- | --- | --- |
| `/s/{siteToken}?form=arrival` | W-01 → 出社時導線 | 現場トークン |
| `/s/{siteToken}?form=break` | W-01 → 休憩時導線 | 現場トークン |
| `/i/{personToken}` | W-03 を個人特定済みで開く | 個人トークン。現場はトークン側に含める |
| `/admin/login` | A-01 | なし |
| `/admin` | A-02 以降 | 管理者セッション |

`form` が欠ける、または `arrival` / `break` 以外のQRはエラーにする。1枚のQRで当日の時間帯からフォームを推測しない（出社用と休憩用を物理で分ける方が現行運用と一致する）。

### 1.3 セッション

| 種別 | 保持するもの | 寿命 |
| --- | --- | --- |
| 作業者（ブラウザ） | 言語、現場トークン、確定した作業者表示名、作業者ID（あれば） | 当日現場日付の終了、または最終操作から30分、または「終了」のいずれか早い方（分数は要確認） |
| 個人トークン | 作業者ID、現場ID、発行元、期限 | 顔認証側と合意した期限。検証はサーバ |
| 管理者 | アカウントID、ロール、参照範囲 | 無操作60分（要確認）。サーバ側セッション |

共有端末対策: 作業者セッションは `localStorage` の長期保存にしない。メモリまたは `sessionStorage` とし、W-10の「終了」とタイマーで削除する。氏名の自動補完を個人スマホだけで使いたい場合は、「この端末は共有しない」をチェックした端末に限る（要確認）。

## 2. 画面遷移

```
作業者
  QR → W-01 現場確定 → W-03 本人確定 → W-04 メニュー
                              │                ├ W-05 出社時 → W-10 完了 → 終了 or W-04
                              │                ├ W-06 休憩時 → W-10
                              │                ├ W-07 セルフチェック
                              │                ├ W-08 応急処置 → W-09 電話
                              │                ├ W-09 緊急連絡
                              │                └ W-11 お知らせ
  個人QR → トークン検証 → 成功なら W-03（項目は埋まった状態）→ 上記
                         → 失敗ならメッセージ → 現場QR導線（現場方針が許可する場合）

管理者
  A-01 ログイン → A-02 一覧 → A-03 詳細（対応記録）
                 → A-04 アラート/未入力
                 → A-05 現場QR
                 → A-06 連絡先・閾値
                 → A-07 設問
                 → A-08 アカウント
                 → A-09 お知らせ
                 → A-10 抽出
```

W-05 と W-06 はメニューからも、対応するQRから直接でも開ける。QRから入った場合、メニューを経由せず1画面目をフォームにして操作回数を増やすのを避ける（推奨）。フォーム画面のフッタから W-07 / W-08 / W-09 へ行ける。

## 3. 作業者画面の項目

共通ヘッダ: 言語切替、現場名、確定済みなら氏名。未確定なら氏名は出さない。

### W-01 QRランディング

| 項目 | 仕様 |
| --- | --- |
| 目的 | 現場とフォーム種別の確定 |
| 表示 | 現場名、これから開くフォーム名（出社時 / 休憩時）、言語切替 |
| 処理 | `siteToken` を検証。無効、停止中現場、期限切れは W-01 のまま理由を表示し、フォームへ進ませない |
| 遷移 | 有効なら W-03 |
| 例外 | オフラインでトークン検証できないときは再試行ボタン。入力値はまだ無い |

### W-02 言語

独立画面にはしない。全作業者画面のヘッダで切替える。切替後も入力済みの数値・はい/いいえは維持する。辞書に無いキーは空欄にせず、欠落をログして日本語を出すのは開発時のみ。本番は欠落キーのある言語を公開不可にする（A-07）。

### W-03 本人の確定

この画面の入力は属性だけである。

| 項目 | 仕様 |
| --- | --- |
| 個人トークン成功 | 氏名、会社名、作業者IDを表示する。編集不可（なりすまし防止）。「次へ」でフォームへ |
| 個人トークンなし / 失敗かつ手入力許可 | 会社（その現場に紐づく協力会社から選択）、氏名（テキスト）。「次へ」 |
| 個人トークン失敗かつ手入力禁止 | 理由と、事務所・職長への連絡を表示。フォームへ進ませない |
| 既に当日セッションがある | 氏名を確認表示。「自分でない」でセッション破棄し、最初から |
| 持たないもの | 血圧、脈拍、睡眠、症状、水分、塩分、顔撮影ボタン |

会社マスタが空の初期現場だけ、会社名の自由入力を許す（要確認）。

### W-04 メニュー

ボタン: 出社時チェック、休憩時報告、セルフチェック、応急処置、緊急連絡、お知らせ。  
当日の出社時チェック送信済みなら、出社時ボタンに「送信済み」を出す。再入力の可否は第6章。休憩時は何回でも入る。  
QRで `form=arrival` のときは本画面をスキップして W-05 へ進んでよい。ヘッダのメニューから他機能へ戻れる。

### W-05 出社時体調チェック

| 順 | フィールド | UI | バリデーション |
| --- | --- | --- | --- |
| 1 | 現場名 | 表示のみ | — |
| 2 | 会社・氏名 | 表示のみ（W-03で確定） | 未確定なら W-03 へ戻す |
| 3 | 最高血圧 | 数値キーパッド | 整数。仮範囲 70–250（要確認） |
| 4 | 最低血圧 | 同上 | 整数。仮範囲 40–150。最高より小さい |
| 5 | 脈拍 | 同上 | 整数。仮範囲 30–200（要確認） |
| 6 | 睡眠 | セグメント選択 | マスタの選択肢から1つ |
| 7 | 体調設問 | 各設問「はい」「いいえ」の2択。未選択が分かる | 全問必須。ラジオの既定値は空。どちらにも初期チェックを付けない |
| 8 | セルフチェックへのリンク | 任意閲覧 | 送信の必須条件にしない |
| 9 | 送信 | 全項目OKで活性 | 二重押し防止 |

送信成功で W-10。失敗時は値を保持して再送。  
画面下部に「具合が悪いとき」から W-08 / W-09 を常時表示する。送信しなくても電話できる。

### W-06 休憩時報告

1画面、スクロールは最小。

| 順 | フィールド | UI |
| --- | --- | --- |
| 1 | 氏名・現場 | 1行表示。違えば「自分でない」 |
| 2 | 水分補給した | はい / いいえ |
| 3 | 塩分補給した | はい / いいえ |
| 4 | 今の体調は問題ない | はい / いいえ（文言と極性は要確認。初期症状の有無と極性を矛盾させない） |
| 5 | 熱中症が疑われる症状がある | はい / いいえ |
| 6 | 応急処置・緊急電話 | 送信前でも遷移可 |
| 7 | 送信 | |

血圧はこの画面に置かない（出社時の測定記録と混ぜない）。作業中の再測定を必須にするかは要確認。現資料の休憩フォームは補給と体調の簡易報告である。

参考イラスト（頭を冷やす、爪を押す、症状が2回以上 等）は設問の横のヘルプであり、保存カラムにはしない。

### W-07 セルフチェック

8項目をイラストと短文で縦に並べる。入力欄は無い。各言語で同じ意味の図を使う（文字を画像に焼き込まない。テキストは辞書）。

### W-08 応急処置フロー

現行フォームにある「重症化を防ぐための発症時フローチャート」に相当する固定コンテンツ。手順の原稿は発注者支給とする（資料の縮小図からは全文を確定できない）。各ステップは辞書化する。電話導線を途中に置く。

### W-09 緊急連絡

| 項目 | 仕様 |
| --- | --- |
| 表示 | 現場名、「工事課員直通」などのラベル、電話番号 |
| 操作 | タップで `tel:` |
| データ | `sites.emergency_phone`。全現場共通の1番号にしない |
| 記録 | 発信ボタン押下を任意でログするか要確認（救護の証跡にはなるが、誤タップも残る） |

資料写真に写っている番号は個人・現場の連絡先なので、本設計の初期データには載せない。

### W-10 送信完了

表示: 受け付けた日時、フォーム種別、判定が赤のときは「職長または現場所長に伝えてください」と W-09 へのボタン（医学的診断結果の表示はしない。色の名称だけを作業者へ出すかは要確認。作業者に「警告」と出すと動揺と、逆に見落としの両面がある）。

ボタン: 「終了（次の人へ）」＝セッション破棄して W-01 相当の待ち。「続ける」＝同一人の W-04。共有端末既定は「終了」を主ボタンにする。

### W-11 お知らせ

対象現場、公開期間、選択言語の本文。未翻訳の言語ではそのお知らせを出さない（他言語へ自動で落ちて意味が変わるのを避ける）。

## 4. 管理者画面の項目

### A-01 ログイン

| 項目 | 仕様 |
| --- | --- |
| 入力 | ログインID、パスワード |
| 失敗 | 残回数を増やしすぎない文言。「アカウントまたはパスワードが違います」 |
| ロック | 仮: 15分に10回失敗で30分ロック（要確認） |
| 成功 | ロールのホームへ。職長・所長の既定フィルタは自範囲 |

作業者フォームへのリンクは置かない。

### A-02 ダッシュボード

現行スプレッドシートの代替。

| 列 | 内容 |
| --- | --- |
| 受信日時 | サーバ時刻 |
| 種別 | 出社時 / 休憩時 |
| 会社 | |
| 氏名 | |
| 現場 | 本部は列を出す。所長は自現場固定で列を省略可 |
| 最高 / 最低 / 脈拍 | 出社時のみ。休憩時は空 |
| 睡眠 | 出社時のみ |
| 設問結果 | 設問ごとの はい/いいえ。警告に効いた設問を強調 |
| 判定 | 通常 / 注意 / 警告。行背景を黄 / 赤 |
| 対応 | 未対応 / 対応中 / 対応済 |

フィルタ: 日付（既定は今日）、現場（権限内）、会社（権限内）、判定、種別。自動更新は短いポーリングまたは手動更新（間隔は要確認。目安15秒）。

行クリックで A-03。

### A-03 回答詳細

全入力値、各ルールの判定結果（どのルールで黄/赤になったか）、対応ステータス、対応メモ、対応者、対応日時。メモ更新は監査。作業者画面にはメモを出さない。

### A-04 アラート／未入力

- 赤かつ未対応のキュー。通知の飛び先と画面の一覧を同じデータにする
- 未入力: 当日、その現場の作業者マスタにいて、出社時チェックが無い人。マスタが無い（方式Aの都度手入力だけ）の間は「まだ誰が来る予定か」が分からないので、未入力一覧は「作業者マスタまたは顔認証連携がある現場」に限定する
- 休憩の抜け: 出社済みで、最終休憩報告から N 分超過（N は現場設定。既定60。要確認）。これは推定であり、休憩の事実と等しくない旨を画面に書く

### A-05 現場・QR

現場の有効/停止、表示名（多言語ラベルが必要なら辞書）、協力会社の紐づけ、出社用トークン再発行、休憩用トークン再発行、QR画像の表示（印刷用）。再発行で旧トークンは即時無効。

### A-06 緊急連絡先・閾値

- 所長: 自現場の電話番号
- 本部: 閾値テーブル（第5章）と、黄を通知するかのスイッチ
- 変更は監査。反映は以降の新規回答から（過去回答の色は再計算するか要確認。推奨は「保存時の判定を保持し、再計算は別操作」）

### A-07 設問

| 属性 | 内容 |
| --- | --- |
| form_type | arrival / break |
| code | 安定キー（回答JSONのキー） |
| polarity | positive（はい＝良好） / negative（はい＝異常） |
| severity_if_bad | none / caution / alert |
| required | bool |
| sort | 表示順 |
| active | 公開 |
| text[lang] | 各言語の設問文。空の言語が残る公開は禁止 |

設問の追加・文言変更は、変更前に集計列の意味が割れないよう `code` を再利用しない（文言を変えるなら新 code）。

### A-08 アカウント

アカウント、ロール、現場（複数可は本部と、兼任所長。要確認）、協力会社（職長は1社）、無効化。パスワード初期化。作業者個人は原則この画面でログインアカウントにしない。作業者マスタ（氏名、会社、外部ID）は別タブとし、顔認証の外部IDをここに置く。

### A-09 お知らせ配信

件名、本文を言語ごと、対象現場、開始終了。配信先プッシュは将来。今は作業者が W-11 を開いたときに見える。

### A-10 抽出

期間、現場、種別。CSVは権限範囲だけ。文字コードは Excel 向け UTF-8 BOM を推奨。ダウンロードを監査。マスキング方針（氏名を出すか）は要確認。熱中症の管理体制としては氏名付きが必要になりやすい。

## 5. 判定ロジック

回答保存時にサーバで計算する。クライアント表示の色はサーバ結果を使う。

### 5.1 設問ルール

```
bad = (polarity == positive  AND answer == no)
   OR (polarity == negative AND answer == yes)
```

`bad` の設問のうち最大の `severity_if_bad` を採用する。`alert` > `caution` > `none`。

### 5.2 数値ルール（仮置き。本番前に差し替える）

単位: 血圧 mmHg、脈拍 bpm。出社時フォームにだけ適用する。

| ルールID | 条件（仮） | レベル | 出典 |
| --- | --- | --- | --- |
| SYS_HIGH | 最高血圧 ≥ 160 | alert | 未確定の仮 |
| SYS_CAUTION | 140 ≤ 最高血圧 ≤ 159 | caution | 未確定の仮 |
| DIA_HIGH | 最低血圧 ≥ 100 | alert | 未確定の仮 |
| DIA_CAUTION | 90 ≤ 最低血圧 ≤ 99 | caution | 未確定の仮 |
| HR_HIGH | 脈拍 ≥ 120 | caution | 未確定の仮 |
| HR_VERY_HIGH | 脈拍 ≥ 140 | alert | 未確定の仮 |
| SLEEP_SHORT | 睡眠が「5時間」またはそれより短い区分 | caution | 仕様書ドラフトの「睡眠が短い＝黄」に合わせた仮 |
| BP_INVERTED | 最高 ≤ 最低 | 保存拒否（入力エラー。判定しない） | 推奨 |
| OUT_OF_RANGE | 第3章の入力範囲外 | 保存拒否 | 推奨 |

睡眠の区分コード（仮）: `ge7`（7時間以上）、`h6`（6時間）、`h5`（5時間）、`lt5`（5時間未満）。`lt5` を選択肢に含めるかは要確認。含めない場合 `h5` を caution。

赤が1つでもあれば総合判定は警告。無く黄があれば注意。無ければ通常。

### 5.3 作業者への見せ方

保存の可否と、必須エラーは作業者に見せる。医学的な「あなたは危険」という断定文は出さない。赤のときは連絡を促す文までとする（文面は要確認）。

## 6. データ（論理）

### 6.1 主なエンティティ

| エンティティ | 主キー | 主な属性 |
| --- | --- | --- |
| organizations | id | 協力会社名 |
| sites | id | 表示名、emergency_phone、active、break_gap_minutes、allow_manual_identity |
| site_tokens | id | site_id、form_type、secret_hash、revoked_at |
| admin_users | id | login_id、password_hash、role、disabled |
| admin_sites | admin_id, site_id | 所長・本部の範囲。本部は全サイトで代替可 |
| workers | id | organization_id、name、external_face_id（nullable）、active |
| worker_site | worker_id, site_id | 入場予定の紐づけ。未入力抽出に使う |
| person_tokens | id | worker_id、site_id、secret_hash、expires_at、used 方針 |
| questions | code | 第4章 A-07 |
| responses | id | site_id、worker_id（nullable）、form_type、respondent_name、organization_name、submitted_at、source（manual / person_token） |
| response_vitals | response_id | systolic、diastolic、pulse、sleep_code。休憩時は行なし |
| response_answers | response_id, question_code | yes / no |
| assessments | response_id | level（normal/caution/alert）、reasons（json） |
| alert_actions | id | response_id、status、note、actor_id、at |
| notices | id | site範囲、period、texts by lang |
| audit_logs | id | actor、action、target、at、ip |

`responses.worker_id` が空なのは手入力送信。氏名は回答時点の文字列をコピーし、後からマスタ改名しても過去回答の表示名は変えない。

### 6.2 出社時の一意性（推奨）

キー案: `site_id + worker_id + business_date + form_type=arrival` が一意。手入力で worker_id が無い場合は `site_id + organization_name + respondent_name + business_date` を同一人の推定に使う（同姓同名は要確認）。再送方針の既定案は「確認ダイアログのあと上書きし、旧値を監査に残す」。

休憩時は一意にしない。同一 worker・同一 site で60秒以内の完全一致再送は1件に吸収する。

### 6.3 個人情報

バイタル列は回答テーブルに残す。顔テンプレート列は無い。保管期間が過ぎた回答の削除または匿名化バッチを将来タスクとして置く（期間は要確認）。

## 7. API（概要）

すべて HTTPS、JSON。

| メソッド | パス | 説明 |
| --- | --- | --- |
| GET | `/api/public/sites/{token}` | 現場名、form、allow_manual_identity、公開設問、緊急連絡先、対応言語。設問はリクエストの言語 |
| GET | `/api/public/person/{token}` | トークン検証。氏名、会社、現場、有効期限。失敗理由コード |
| POST | `/api/public/responses` | 回答。現場トークン必須。個人トークンは任意。サーバで再検証・再判定 |
| POST | `/api/admin/login` | セッション発行 |
| POST | `/api/admin/logout` | |
| GET | `/api/admin/responses` | 範囲内一覧 |
| PATCH | `/api/admin/responses/{id}/action` | 対応ステータス |
| CRUD | `/api/admin/sites` ほか | マスタ。ロールで拒否 |

公開APIはレート制限をかける（共有QRの悪用）。管理APIは未認証を401、範囲外を404（存在の漏洩を減らす）に近い扱いにする。

回答POSTのボディ（出社時）:

```json
{
  "siteToken": "...",
  "personToken": null,
  "formType": "arrival",
  "organizationName": "…",
  "respondentName": "…",
  "vitals": { "systolic": 120, "diastolic": 80, "pulse": 70, "sleepCode": "ge7" },
  "answers": [{ "code": "feel_ok", "value": "yes" }]
}
```

休憩時は `vitals` を送ってはならない。送られた場合は400にする（画面の取り違えをサーバで拒否する）。

## 8. 顔認証連携のシーケンス（低コスト）

顔認証製品の内部は範囲外。本システムが受ける契約だけを書く。

1. 作業者が既存の顔認証端末で入場認証する（本アプリの外）
2. 端末またはその連携画面が、本システムの事前共有鍵で署名したURLをQR表示する  
   例: `https://{host}/i/{token}`  
   token の中身（サーバが検証できること）: `workerExternalId`、`siteId`、`exp`、署名
3. 作業者のスマホが URL を開く
4. APIが署名と期限と現場の有効を確認し、`external_face_id` から workers を引く
5. 該当 worker が無ければ、その場で作るか、拒否してマスタ登録を待つか（要確認。推奨は「会社と氏名がペイロードにあり現場が許可なら仮登録」）
6. W-03 に氏名を表示する。バイタルは空
7. 作業者が W-05 または W-06 を送る。`responses.source = person_token`、`worker_id` を埋める

高コスト案を増やすときの差分: 手順2のQRを必須とせず、管理APIが顔認証側の「本日の入場者」を取り込み、A-04 の未入力と突合する。体調POSTの項目は増やさない。

障害: 署名鍵のローテーション手順、時刻ずれによる期限誤判定（許容秒数を要確認）。

## 9. 多言語の設計

| 対象 | 置き場所 | 切替 |
| --- | --- | --- |
| ボタン、エラー、画面タイトル | フロントの辞書 | ヘッダ |
| 設問文 | DB `questions.text[lang]` | APIが言語を選んで返す |
| 応急処置の手順 | 辞書またはCMS。自動翻訳しない | ヘッダ |
| お知らせ | notices の言語別本文 | 選択言語の1件 |
| 判定理由（管理画面） | 管理者向けは日本語固定でよいか要確認。外国人の職長がいるなら管理画面も辞書化する（推奨は管理画面も同じ言語切替） |

言語コード（仮）: `ja`, `en`, `id`, `vi`, `zh-CN`。  
初期表示: 保存された選択 → 無ければ `Accept-Language` の前方一致 → `ja`。  
数値と日付の表記は日本語ロケール固定でも業務上足りる（現場が日本）。文だけ切替える。

設問を公開するトランザクション: 有効言語すべてに `text` があること。

## 10. 通知

| イベント | 条件 | 宛先 | 本文に入れるもの |
| --- | --- | --- | --- |
| 警告 | assessment.level = alert | その現場の所長、その会社の職長、通知ONの本部 | 現場、会社、氏名、種別、受信時刻、どのルールか、管理画面URL。測定値そのものをメールに載せるかは要確認（メール転送の漏洩） |

## 11. 監査と権限チェック

すべての管理系更新で `audit_logs` を1行書く。一覧の画面表示まではログしない（量が過大）。抽出、詳細の初回オープン、対応メモ、マスタ変更、ログイン成功/失敗は書く。

権限はAPIで検査する。フロントのメニュー非表示は補助。

| ロール | responses の WHERE |
| --- | --- |
| hq | 制限なし |
| site_manager | site_id in admin_sites |
| foreman | organization_id = その職長の会社 AND site_id in admin_sites |

職長が複数現場の自社を見るかは `admin_sites` の行で表す。
