## 1. 背景と目的

### 1.1 背景（確定）

改正労働安全衛生規則に基づき、令和7年6月1日から職場の熱中症対策が強化されている。改善事例の現場では、紙の「水分・塩分・体調 確認表」を1時間ごとに現場内へ移動して記入していた。

| 観点 | 紙運用（As-Is） |
| --- | --- |
| 時間 | 平均移動 約3分（往復約6分）。毎日の準備・集計 約30分 |
| 紙 | 1現場あたり 約15枚/日 × 105営業日 ≒ 年間約1,600枚（入場数により変動） |
| 管理 | 記入が目的化し、チェック機能が形骸化する懸念。初期症状の把握が遅れるリスク |
| 対応範囲 | 「チェックするのみ」にとどまり、発症時フローの周知、緊急連絡、多言語が不足 |

中間措置として、現場ごとのQRコードから Googleフォームへ入力し、スプレッドシートで自動集計する運用に移行済みである。休憩所・クールスポットで1分未満の入力、紙の消費ゼロ（QR発行用紙を除く）、「黄：注意」「赤：警告」の色分けを実現している。ブラウザ翻訳で多言語表示（資料上は240言語）も試行している。

中間措置で残っている限界（独自アプリ＝本システムの理由）は次のとおり。

- 発症者・異常値を管理者へ自動通知できない（色分けの目視のみ）
- 会社名・氏名を手入力している（既存の顔認証システムと未連携）
- 多言語がブラウザ翻訳依存である
- 権限が現場単位のフォーム運用で、本部 / 現場所長 / 協力会社・職長に分けられない
- 作業者への入力リマインド・お知らせがない

### 1.2 目的（確定）

作業者の出社時体調記録と、作業中の休憩・補給報告を Webアプリでデジタル化し、次を同時に満たす。

1. 入力を現場の休憩所などで1分未満に保つ（時間短縮）
2. 紙の確認表を廃し、クラウドでリアルタイム集計する（ペーパーレス）
3. 不調者を見逃さず、初期対応・緊急連絡・関係者周知まで含めた管理体制にする（重症化防止、重傷者ゼロ）

### 1.3 今回の範囲と将来範囲

| 区分 | 内容 |
| --- | --- |
| 今回（MVP） | 作業者Web（出社時チェック、休憩時報告、セルフチェック閲覧、応急処置、緊急連絡）、管理者Web（一覧・色分け・権限制御）、異常時通知、アプリ内多言語、現場QR起動 |
| 今回に設計だけ残す | 既存顔認証システム連携（低コスト案を第一候補、高コスト案は接続条件が分かり次第） |
| 将来 | 新規入場者教育、安全衛生チェックシートなど他業務への横展開。データ構造は拡張可能な形にする。画面・機能は今回作らない |

## 3. 業務フロー（確定した業務をWebアプリに対応づけたもの）

### 3.1 前日

- 作業者: 睡眠など自己管理（アプリの入力対象外。翌朝の睡眠時間として申告する）
- 管理者: 休憩所・案内場所に「出社時」「休憩時」のQRを設置し、使い方を周知する

### 3.2 出社時（作業前スクリーニング）

1. 作業者が血圧・脈拍を測定する（測定器は現場の既存機器。アプリは数値の記録先）
2. 出社時QRをスマホの標準カメラで読む
3. Webアプリが当該現場の出社時フォームを開く
4. 本人情報を確定する（手入力、または顔認証連携による自動補完。詳細は第5章）
5. 最高血圧・最低血圧・脈拍・前日の睡眠時間・仕事前の体調設問に回答する
6. 予防のセルフチェック（イラスト）を確認できる
7. 送信後、管理者ダッシュボードへ即時反映する
8. 注意（黄）または警告（赤）なら管理者へ通知する

### 3.3 作業中（目安1時間ごと）

1. 作業者が最寄りの休憩所・クールスポットへ移動する
2. 休憩時QRから休憩時報告を1分未満で送る（水分・塩分・現在の体調）
3. 管理者は入力状況をリアルタイムで見る
4. 入力漏れ・異常は一覧と通知で把握する

### 3.4 緊急時

1. 作業者（または周囲）がアプリ内の発症時フローチャートを見る
2. 画面上の現場直通番号へワンタップで電話する
3. 管理者は救護と搬送の判断・指示を行う（判断そのものは人の業務。アプリは連絡と記録を支える）

## 4. システム構成案（推奨）

```
[作業者スマホ/タブレット] --HTTPS--> [Webアプリ（作業者UI）]
[管理者PC/タブレット]     --HTTPS--> [Webアプリ（管理コンソール）]
                                         |
                          +--------------+--------------+
                          | アプリサーバ / API          |
                          | 認証・権限・判定・通知       |
                          | DB（回答、現場、利用者、監査）|
                          +------+---------------+-----+
                                 |               |
                    [メール / Web Push]   [既存顔認証システム]
                                          低コスト: QR/一時URL
                                          高コスト: API同期（要確認）
```

| 要素 | 方針 |
| --- | --- |
| クライアント | レスポンシブWeb。作業者はスマホ幅、管理者はPC幅を主とする。共有タブレットも動作対象 |
| 起動 | 現場QRは `https://{host}/s/{siteToken}?form=arrival\|break` のようなURLを開く。アプリ側にカメラ実装は必須としない（標準カメラのQR読取） |
| サーバ | クラウド上のAPIとDB。回答は保存と同時に判定し、黄/赤なら通知を発火する |
| 通知 | 第一候補はメール＋管理画面の未対応バッジ。ブラウザのWeb Pushはホーム画面追加などの制約があるため、到達保証の主経路にはしない（要確認） |
| PWA | ホーム画面追加は任意。プッシュを主機能にする場合のみ検討 |
| オフライン | 現場電波が不安定でも送信失敗が分かること。完全オフライン蓄積は要確認 |

ネイティブアプリ（ストア審査、端末ごとのインストール、バックグラウンド通知の確実性、カメラとの密結合）は比較資料にあるが、本書の対象はWebアプリである。

## 5. ログイン要件

ログインは「管理者の本人認証」と「作業者の現場入場・誰の回答かの特定」で役割が異なる。体調チェックの設問はこの章に含めない。

### 5.1 管理者ログイン（推奨・必須機能）

- IDとパスワードで管理コンソールに入る。パスワード再設定手段を持つ
- ログイン後の操作範囲はロールと所属（現場、協力会社）で制限する
- 無操作が続いたセッションは切る（時間は要確認。目安60分）
- 連続失敗で一時ロックする（回数は要確認）
- ログイン・権限変更・抽出は監査ログに残す
- 本部がアカウントを発行する。自己登録はしない
- 社内SSOに乗せるかは要確認。資料には無い

### 5.2 作業者の起動と本人特定（推奨）

1時間ごとの入力を1分未満に保つため、作業者に毎回のパスワード入力は求めない。

| 方式 | 内容 | 位置づけ |
| --- | --- | --- |
| A. 現場QR＋属性入力 | QRで現場とフォーム種別が決まる。会社名・氏名は入力する。同一ブラウザでは次回補完してよい | MVPの基本。現行Googleフォームに最も近い |
| B. 個人QR / 一時URL（顔認証・低コスト連携） | 入場時の顔認証が払い出した個人識別QRまたは一時トークン付きURLで開き、作業者ID・氏名・会社を自動セットする | 連携の第一候補。詳細は第7章 |
| C. API同期（顔認証・高コスト連携） | 入場ログと未入力者をサーバ間で突合する | 既存システムのAPIが公開されるまで実装しない |

方式Aでも、端末に残った前任者のプロフィールで送信しない制御が要る（共有タブレット。第11章）。

作業者に「アカウントパスワード画面」と「体調フォーム」を同一画面にしない。

### 5.3 現場QRのセキュリティ（推奨）

- QRのトークンは推測されにくいランダム値とする。連番の現場IDだけを公開パラメータにしない
- トークンは現場ごとに再発行できる。旧トークンは無効化できる
- トークンが漏れても、できるのは当該現場のフォーム表示と回答送信までとする。他現場・管理機能・他者のバイタルは見えない
- なりすまし（他人の氏名での送信）は方式Aの残リスクとして記録する。抑止は方式B/Cで強化する

## 6. アンケート（体調チェック）要件

本章は健康状態の申告である。顔写真、顔特徴量、入場ゲートの認証結果は設問にしない。

### 6.1 フォームは2種類（確定）

現場には次の2つのQRを置く。

| フォーム | 使うタイミング | 完了の目安 |
| --- | --- | --- |
| 出社時体調チェック | 作業前に1回 | 測定値の転記を含め、現場で迷わず終われること |
| 休憩時報告 | 作業中、目安1時間ごと | 1分未満 |

### 6.2 出社時の項目

資料（仕様書ドラフトおよび集計シートの列）から読み取れる項目。設問の原文と「はい」の意味は画像からは確定できない（要確認）。

| ID | 項目 | 型 | 必須 | 備考 |
| --- | --- | --- | --- | --- |
| A-01 | 現場 | 自動 | ○ | QRの現場。作業者は選び直さない（誤現場防止） |
| A-02 | 会社名 | テキストまたはマスタ選択 | ○ | 方式B/Cでは自動。手入力時は候補から選ぶことを推奨 |
| A-03 | 氏名 | テキスト | ○ | 同上 |
| A-04 | 最高血圧 | 整数 mmHg | ○ | 現実的な範囲チェック（範囲値は要確認） |
| A-05 | 最低血圧 | 整数 mmHg | ○ | 最高 > 最低 |
| A-06 | 脈拍 | 整数 bpm | ○ | |
| A-07 | 前日の睡眠時間 | 選択 | ○ | 資料上の例: 7時間以上 / 6時間 / 5時間。5時間未満の有無は要確認 |
| A-08〜 | 仕事前の体調・準備 | はい / いいえ | ○ | 複数列。集計シート上は少なくとも数問。原文要確認 |
| A-xx | 熱中症の初期症状・疑い | はい / いいえ | ○ | 疑い「あり」を警告に接続する。設問の聞き方（疑いが無い、か、疑いがある、か）を固定する |

送信時にタイムスタンプ（サーバ時刻）を自動記録する。作業者には自由記述欄を置かない（多言語と1分入力を守るため。要確認でオプション化可）。

### 6.3 休憩時の項目（確定している趣旨、原文は要確認）

| ID | 項目 | 型 | 必須 |
| --- | --- | --- | --- |
| B-01 | 現場 | 自動 | ○ |
| B-02 | 会社名・氏名 | 自動（セッションまたは個人QR）/ 最短入力 | ○ |
| B-03 | 水分補給したか | はい / いいえ | ○ |
| B-04 | 塩分補給したか | はい / いいえ | ○ |
| B-05 | 現在の体調 | はい / いいえ、または段階 | ○ |
| B-06 | 熱中症の初期症状の有無 | はい / いいえ | ○（推奨） |

入力画面の参考UIには、休憩時チェックのラジオとあわせて、症状イラスト（頭・首を冷やす、爪を押す等）と応急処置への導線がある。イラストは設問の回答値ではなく、回答を助ける表示とする。

### 6.4 セルフチェック（閲覧。回答値と分ける）

次の8項目をイラスト付きで示す（確定。文言の訳は多言語対象）。

1. こまめな水分補給
2. 直射日光を避ける
3. 湿度・室温に注意する
4. 涼しい服装にする
5. 冷却グッズを活用する
6. 適切な塩分補給
7. 適切な休憩時間
8. しっかり眠る

これは予防の周知であり、黄/赤の判定入力には使わない。出社時・休憩時のどちらからでも開ける。

### 6.5 判定（趣旨は確定、数値閾値は要確認）

| 表示 | 資料上の意味 | ドラフトでの接続 |
| --- | --- | --- |
| 通常 | 色分け対象外 | 通知しない |
| 黄：注意 | 血圧・脈拍が閾値を超える、睡眠時間が短い 等 | ダッシュボード着色。通知するかは要確認 |
| 赤：警告 | 体調設問の「不調」、熱中症初期症状の疑い | ダッシュボード着色＋管理者へ即時通知 |

1件の回答が黄と赤の両方に当たる場合は赤を優先する（推奨）。

「いいえ」を常に赤にしてはならない。設問には次の2極性がある。

- 良い状態を聞く（例: 仕事前の体調は問題ない / 水分補給した）→ 「いいえ」が注意または警告
- 悪い状態を聞く（例: 熱中症の疑いがある）→ 「はい」が警告

各設問に極性と、黃に上げるか赤に上げるかをマスタで持たせる。

血圧・脈拍・睡眠の数値閾値は資料に無い。産業医または発注者の確認前に本番値として固定しない。基本設計書には仮置きテーブルを置き、設定画面で本部が変更できる前提にする。

### 6.6 回答の訂正と多重送信（推奨・要確認）

- 同一作業者・同一現場・同一日の出社時チェックは1件を原則とする。再送は上書きか、訂正理由付きの追記かを要確認
- 休憩時は同日複数件を許す。短時間の連続送信（例: 60秒以内）は二重タップとして1件にまとめる
- 作業者は送信後に他人の回答を編集できない。誤送信の訂正は管理者（現場所長または本部）が監査つきで行う

## 7. 顔認証の要件（ログイン／本人特定。体調判定ではない）

### 7.1 役割の分離（本ドラフトの前提）

| | 顔認証連携 | 体調チェック |
| --- | --- | --- |
| 答えたいこと | 誰が、どの現場の入場者として回答したか | その人の血圧・脈拍・睡眠・自覚症状・補給状況 |
| 入力 | 既存顔認証システムが持つ識別子、氏名、会社 | 第6章の設問 |
| 画面 | 起動時の本人確定（W-03） | 出社時フォーム（W-05）、休憩時フォーム（W-06） |
| 判定 | 入場済みか、トークンが有効か | 黄/赤 |
| 顔画像 | 本アプリは保持しない（推奨） | 使わない |

資料の「顔認証システムと連携」は、改善報告 No.1-3 の残課題である。記載は名称のみで、製品名、設置形態（ゲート、室内の大型モニタ等）、APIの有無は不明。実在する既存システムとの連携を指し、本アプリがカメラで顔を撮影して熱中症を推定する機能ではない。

本アプリのカメラ顔認証（端末内またはクラウド顔照合）は要件に含めない。

### 7.2 低コスト案（第一候補・推奨）

既存ゲート／端末が認証成功時に出す「個人識別QR」または「一時トークン付きURL」を、スマホ標準カメラで開く。

- サーバはトークンを検証し、作業者ID・氏名・会社名・現場をフォームへセットする
- トークンは短命（目安: 当日の就業時間、または数分〜数時間。要確認）とし、使い回しと期限切れを拒否する
- Webアプリと顔認証システムの間に常時APIは置かない
- 体調の数値・はい/いいえは、トークン検証の後に作業者が入力する
- トークン検証に失敗した場合は、現場QR＋手入力（方式A）へ落とすか、入力を止めるかを現場運用で選ぶ（要確認）。入力を止めすぎると、ゲート障害の日に体調記録がゼロになる

### 7.3 高コスト案（条件付き）

既存システムのクラウドDBまたはオンプレとAPIで接続し、入場ログと回答をリアルタイムに結び、未入場者は体調入力できない、未入力者を自動抽出する。

着手条件（すべて要確認）:

- 製品名、API仕様、認証方式、ネットワーク到達性
- 個人識別子の対応表（顔認証側ID ↔ 本システム作業者ID）
- 顔画像・生体特徴量を本システムへ送らない契約
- 障害時に体調入力を継続するかの運用判断

### 7.4 大型モニタ設置型（要確認）

打合せメモに、室内の大型モニタで顔認証している形態があり得る、とある。その場合の起動元が「個人スマホ」か「共有キオスク」かでW-03のUIが変わる。キオスクでは送信完了後に必ずセッションを破棄する。

## 8. 多言語化要件

### 8.1 方針（確定に近い。言語セットは要確認）

ブラウザの自動翻訳に依存しない。画面文言、ボタン、設問、エラー、応急処置フロー、緊急連絡のラベルをアプリ内の辞書で切り替える。

資料にある言語の候補: 日本語、英語、インドネシア語、ベトナム語、中国語。インドネシア語は現行フォームの翻訳実例として登場する。初期リリースの言語リストは要確認。

### 8.2 低コスト案（第一候補・推奨）

- 画面に言語切替（例: JA / EN / ID / VI / ZH）を常時表示する
- 翻訳済みの辞書（i18n）を持つ。5〜6言語
- 追加設問は、辞書に訳を足してから公開する。訳が無い言語では公開できない（サイレントに日本語だけ出さない）

### 8.3 高コスト案（将来または本文の自動翻訳）

管理者が書いた自由文（お知らせ、新しい設問、緊急時の補足）を翻訳APIで他言語へ展開する。従量課金と用語の誤り（症状名）があるため、応急処置の医療手順は自動翻訳の原文にしない。固定フローチャートは人手の訳を正とする。

### 8.4 翻訳しないもの

- 氏名、会社名、現場名の固有名詞
- 電話番号
- 作業者が入力した数値

言語を切り替えても入力途中の値は保持する。初期言語はブラウザ設定を見て、なければ日本語。選択は端末に記憶する。

## 11. 例外・非機能（要件としての最低線）

| 項目 | 要件 |
| --- | --- |
| 対応端末 | 直近2世代程度の iOS Safari、Android Chrome。管理画面はデスクトップ Chrome / Edge / Safari |
| 操作時間 | 休憩時報告は項目数を増やしすぎない。回線が普通なら送信完了まで1分未満を目標とする |
| 個人情報 | 氏名、会社、血圧、脈拍、自覚症状は要配慮の健康情報。目的外利用をしない。保管期間は要確認 |
| 通信 | TLS。管理APIは認証必須。作業者の送信APIは現場トークン（と、あれば個人トークン）を検証 |
| 共有端末 | 送信完了と「終了」で氏名・トークンを消す。一定時間操作が無ければ自動で消す |
| 障害 | 保存失敗時は未送信であることを画面に残し、黙って成功扱いしない |
| 監査 | 管理者の閲覧のうちエクスポート、回答訂正、権限変更を記録 |
| 免責表示 | 本アプリは診断機器ではない。測定と救護判断は現場の人の手順に従う（表示文は要確認） |
| 時刻 | 判定と集計の「日」は現場タイムゾーン（日本時間） |

## 12. 受入の観点（コア）

1. スマホの標準カメラで現場QRを開くと、インストールなしで出社時または休憩時のフォームが出る
2. 出社時に会社・氏名・血圧・脈拍・睡眠・体調設問を送り、管理画面へ当日分として色付きで出る
3. 休憩時フォームは水分・塩分・体調を短い操作で送れる
4. 赤判定の回答で、権限を持つ管理者に通知が届き、ダッシュボードが赤になる
5. 職長は自社以外を見られない。現場所長は他現場を見られない
6. 言語を切り替えると、設問・ボタン・応急処置・エラーが選択言語になる
7. 顔認証連携（低コスト）を有効にした現場では、個人QRで氏名・会社が埋まり、その画面に体調設問が混在しない
8. 顔認証のトークンが無くても、方針で許可した現場では現場QR＋手入力で体調記録を残せる
9. 応急処置と緊急電話は、フォーム送信の前後どちらでも開ける
10. 共有タブレットで送信完了後、次の利用者が前任者の氏名のまま送れない
