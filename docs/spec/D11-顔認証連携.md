## 1. 目的

既存の入場用の顔認証から、誰の回答かを受け取ることを定義する。

## 2. 適用範囲

定義すること: 受け取る属性、受け取り方の候補、本システムが顔を撮らないこと。

定義しないこと: 体調の設問と値（D07、D08）、判定（D09）、ログイン画面の部品（D06 の W-03 は結果を表示するだけ）。

## 3. 参照

- `report-0924.pdf` の「すでに運用中の顔認証システムと連携」
- D02 の設計のみ
- `spec-heatstroke-app.pdf` の低コスト案と高コスト案

## 4. 用語

| 用語 | 意味 |
| --- | --- |
| 個人トークン | 入場認証のあと、本システムが検証できる一時のURLまたはQR |
| 外部ID | 既存システム側の作業者の識別子 |
| 低コスト | 常時のAPIを持たず、トークンで属性を埋める |
| 高コスト | APIで入場ログと未入力を突き合わせる。今回は機能にしない |

| ID | 要求 | 状態 |

## 6. 仕様

資料にある名称は「顔認証システム」だけである。製品名、APIの有無、ゲートか室内の大型モニタかは未決（Q.11.01）。

低コストの手順（D11-R03、D11-R04）:

1. 入場認証は本システムの外で終わる。
2. 相手が署名付きURLを出す。検証できる項目は外部ID、現場、期限、署名。
3. 本システムは署名、期限、現場を見て外部IDから作業者を引く。
4. W-03 に氏名と会社を表示する。この時点で D08 の値は空である。
5. 作業者が設問を送る。回答の出所は person_token、作業者IDをヘッダに入れる。

高コストを足すときの差分は、未入力一覧の母集団に「当日の入場者」を加えることである。回答の値の配列は増やさない。

大型モニタの共有端末では、送信完了の終了でセッションを消す（寿命の定義は D10、部品は D06）。

## 7. 他領域との受け渡し

渡すもの: 作業者ID、氏名、会社、現場、トークンの成否。D10 がセッションに載せる。D06 の W-03 が表示する。

受け取らないもの: `Q-*` の値。
